# Сервер организации: готовые образы и HTTPS

Этот вариант предназначен для отдельного Linux-сервера организации. Приложение,
фоновый обработчик, PostgreSQL, Caddy и ежедневное резервирование запускаются через
Docker Compose. На сервере не нужны сборка Python-зависимостей, Node.js, ZIP-архивы
или PowerShell. Для рабочего сервера используйте `compose.prod.yaml`; локальная
инструкция остаётся в [install-windows.md](install-windows.md).

## Что подготовить

- Linux-сервер с Docker Engine и плагином Docker Compose v2, Python 3 и Git.
  Учётная запись должна иметь право запускать Docker. Членство в группе `docker`
  фактически даёт полномочия администратора сервера; выдавайте его ограниченно.
- Реальный домен, например `monitoring.organization.ru`. Его записи A и, если
  используется IPv6, AAAA должны указывать на этот сервер. Ошибочную AAAA-запись
  следует удалить или исправить.
- Доступность TCP 80 и 443 для выдачи и продления публичного сертификата; UDP 443
  нужен только для HTTP/3. Другие порты контейнеров наружу не публикуются.
- Исходящие HTTPS-запросы к GHCR, центру выдачи сертификатов и зарегистрированным
  статистическим источникам. К OpenAI обращение выполняется только после отдельного
  включения; по умолчанию оно выключено.
- Постоянный диск для PostgreSQL, документов и резервных копий; контроль свободного
  места и отдельное защищённое хранилище для копии секретов.

При rootless Docker Linux может запрещать публикацию портов ниже 1024. ИТ-служба
должна заранее разрешить публикацию 80/443 для выбранного Docker или подготовить
согласованный внешний прокси. Скрипты проекта не меняют системные `sysctl` и
правила firewall.

Размещайте каталог проекта внутри приватного каталога, доступного только серверному
администратору, например `~/services` с правами `0700`. Не размещайте его в каталоге,
который раздаёт веб-сервер. Скрипт не меняет права существующего родительского
каталога автоматически.

Первый выпуск пакета GHCR может оказаться закрытым. Если `pull` сообщает `denied`,
владелец должен либо открыть доступ к пакетам, либо выдать серверу учётные данные с
правом `read:packages`. Для частного пакета выполните интерактивный
`docker login ghcr.io --username ИМЯ_УЧЁТНОЙ_ЗАПИСИ`; токен вводите в приглашении,
не в командной строке, README или `.env.prod`. Доступ к закрытому репозиторию может
также потребовать `repo` и разрешение организации на пакет. Предпочтительна
отдельная служебная учётная запись с минимальными правами.

## Первый запуск

Войдите на сервер под подготовленной учётной записью и выполните команды внутри
защищённого каталога. Замените домен своим:

```sh
git clone https://github.com/kd170703/product.git
cd product
sh scripts/setup-server.sh monitoring.organization.ru
sh scripts/server.sh pull
sh scripts/server.sh up -d
```

Скрипт создаст `.env.prod` из примера и файлы секретов в `.secrets/`. Повторный
запуск сохраняет существующие настройки и значения. Значения секретов не
выводятся. Файл `.env.prod` имеет права `0600`, каталог `.secrets` — `0700`.
Сами секреты имеют права `0444`: так Docker Compose может смонтировать их для
процесса приложения с UID 10001, а закрытый родительский каталог защищает их на
хосте. Это файловые секреты Compose, а не зашифрованное хранилище Docker Swarm.

Проверьте `.env.prod`: в нём находятся только домен, адреса образов, имя базы,
модель GPT и настройки резервирования. Пароли и ключи туда не добавляют. Если
настройки создаются впервые, домен обязателен; без него скрипт завершится с ошибкой
до создания секретов. Повторный запуск без аргумента допускается и не меняет
существующие настройки. В конфигурации обязательна двухфакторная аутентификация.

```sh
sh scripts/server.sh ps
sh scripts/server.sh logs --tail=100 web worker caddy backup
sh scripts/server.sh exec web python manage.py createsuperuser
```

Откройте `https://ВАШ_ДОМЕН`, войдите созданной учётной записью и настройте приложение
аутентификатора для второго фактора. Сохраните выданные резервные коды в защищённом
хранилище. Администратор создаёт остальные учётные записи и назначает роли по
[инструкции о правах](roles.md). Случайную потерю всех факторов следует решать через
документированную административную процедуру, а не отключением защиты для всех.

Первый запуск автоматически применяет миграции и подготавливает статику. Проверка
`/health/` выполняется внутри контейнера по HTTP; это исключение только для проверки
доступности. Пользовательские страницы требуют HTTPS. `ps` должен показывать
здоровое состояние `db`, `web` и `backup`; `worker` и `caddy` должны работать без
циклических перезапусков. Наличие контейнера само по себе не подтверждает успешную
загрузку внешних данных: её результат смотрят в журнале обновлений приложения.

## Что сохраняется и что доступно снаружи

Проект Compose называется `product-prod` и не смешивает данные с локальным
`compose.yaml`. Именованные тома `pgdata`, `media`, `staticfiles`, `caddy_data` и
`caddy_config` сохраняются при перезапуске и обычном `down`. **Не выполняйте
`down -v` на рабочем сервере:** этот параметр удаляет тома с данными.

Только Caddy публикует 80/443. У Django и PostgreSQL нет портов на хосте. База и
резервирование находятся во внутренней сети; приложение и обработчик имеют
исходящий доступ для источников. Caddy заменяет переданные клиентом
`X-Forwarded-For`, `X-Forwarded-Proto` и `X-Forwarded-Host` фактическими параметрами
соединения. Защита от перебора учитывает адрес клиента через этот единственный
прокси. Не публикуйте порт Django и не добавляйте внешний прокси без пересмотра
доверия к заголовкам; иначе все пользователи могут оказаться за одним адресом или
адрес можно будет подделать.

Файлы приложения доступны пользователям через проверку прав Django. Caddy не
раздаёт `media` напрямую. Временные файлы контейнеров находятся в `tmpfs`; корневая
файловая система приложения и резервировщика доступна только для чтения.

`incoming/` — согласованная папка импорта, примонтированная только для чтения.
Новые файлы должны быть читаемы UID 10001: типовой вариант внутри закрытого
каталога сервера — права `0755` для `incoming/` и `0644` для импортируемых файлов.
Скрипт задаёт такие права только новому каталогу. Существующие ограничения не
ослабляются; при необходимости администратор может настроить ACL вместо общих
прав чтения. Просмотр и настройка загрузок выполняются в интерфейсе приложения.

## Обновление и закреплённые версии

GitHub Actions проверяет код и публикует готовые Linux/amd64-образы приложения и
резервирования; процесс описан в [image-publishing.md](image-publishing.md).
Тег `main` обновляется; тег `sha-ПОЛНЫЙ_SHA_КОММИТА` обозначает
конкретную опубликованную версию. Для контролируемого выпуска укажите в
`.env.prod` одинаковый SHA для обоих образов:

```dotenv
APP_IMAGE=ghcr.io/kd170703/product:sha-ПОЛНЫЙ_SHA_КОММИТА
BACKUP_IMAGE=ghcr.io/kd170703/product-backup:sha-ПОЛНЫЙ_SHA_КОММИТА
```

Для дополнительной фиксации можно использовать проверенные адреса
`image@sha256:ДАЙДЖЕСТ`. Файл Compose не содержит `build`; сервер всегда скачивает
готовые образы. Перед обновлением сохраните текущие ссылки на образы и выполните
резервирование по [инструкции резервирования](backups.md).

```sh
sh scripts/server.sh exec backup /usr/local/bin/backup-now.sh
sh scripts/server.sh pull
sh scripts/server.sh up -d
sh scripts/server.sh ps
```

После изменения инфраструктурных файлов получите проверенный коммит репозитория
и просмотрите изменения `.env.prod.example`, `compose.prod.yaml` и `Caddyfile`.
Существующий `.env.prod` не перезаписывается. Код и шаблоны внутри приложения
обновляются вместе с образом; сборка на сервере не требуется.
После изменения `Caddyfile` примените конфигурацию командой
`sh scripts/server.sh up -d --force-recreate caddy`: административный API Caddy
отключён, изменение содержимого примонтированного файла само по себе его не
перезагружает.

Откат к предыдущему образу допустим только при совместимости схемы базы.
Не рассчитывайте, что смена тега отменяет миграции. Для несовместимой миграции
нужны восстановление соответствующей резервной копии и проверка на отдельном
окружении. После установки секрет базы нельзя просто заменить: пароль существующей
роли PostgreSQL автоматически от изменения файла не меняется.

Журналы Docker ограничены тремя файлами по 10 МБ на сервис. Это ограничение объёма, а не срока хранения; срок и передачу в систему мониторинга устанавливает организация. Тела запросов не включаются в журнал доступа приложения.

## Резервирование и контроль работы

Сервис `backup` делает зашифрованный снимок PostgreSQL и документов при первом
запуске, затем ежедневно в `03:00` по `Europe/Moscow`. Расписание задают
`BACKUP_TIME` и `BACKUP_TIMEZONE`. Настройки хранения по умолчанию: 30 ежедневных,
4 еженедельных и 12 ежемесячных снимков. Репозиторий Restic хранится в
`BACKUP_DIRECTORY` (по умолчанию `./backups-prod/restic`). Каталог должен находиться
на постоянном диске; перенос на другой путь не переносит существующие снимки.
Если указан собственный путь `BACKUP_DIRECTORY`, заранее создайте его с правами
`0700` на выбранном диске. При больших базах увеличьте `tmpfs /work` в Compose:
лимит по умолчанию — 256 МБ для промежуточного дампа и кеша Restic.

Снимок базы создаётся до копирования документов. Исходные публикации и версии
отчётов приложение сохраняет отдельными файлами; будущие изменения не должны
перезаписывать файл, уже связанный со снимком базы. Порядок восстановления,
принудительный снимок, проверка репозитория и контроль давности копий описаны в
[backups.md](backups.md).

Потеря `.secrets/backup_password` означает потерю доступа к зашифрованным копиям.
Секреты и `.env.prod` сохраняйте отдельно от репозитория резервирования. Копия
только на том же диске защищает от ошибки в базе, но не от отказа сервера: нужна
вторая копия в согласованном защищённом хранилище организации и регулярная проба
восстановления. Расположение второй копии согласуют до переноса рабочих данных.

## Закрытая сеть и корпоративные сертификаты

Конфигурация `Caddyfile` рассчитана на публичный DNS и автоматический сертификат
ACME. Если сервер доступен только из VPN/локальной сети, ИТ-служба выбирает один
из вариантов:

- Корпоративный сертификат: смонтировать сертификат и ключ только для чтения в
  Caddy и добавить `tls /certs/fullchain.pem /certs/private-key.pem` в блок домена.
  Закрытый ключ нельзя помещать в репозиторий. Продление сертификата остаётся
  обязанностью корпоративной инфраструктуры.
- Внутренний центр Caddy: добавить `tls internal` и распространить корневой
  сертификат на все рабочие устройства через ИТ-службу. Браузеры не доверяют
  такому сертификату автоматически. Том `caddy_data` хранит внутренний CA и должен
  быть защищён и сохранён.
- DNS challenge ACME: нужен отдельный проверенный образ Caddy с модулем
  конкретного DNS-провайдера и безопасно переданный токен. Базовый образ в этом
  проекте не включает такие модули.

При TLS-терминации на корпоративном балансировщике конфигурацию прокси и правила
доверия к клиентскому адресу необходимо согласовать отдельно. Простое отключение
HTTPS в Django не заменяет эту настройку. Реальная выдача сертификата и работа
корпоративной сети требуют домена и доступа ИТ-службы; локальная проверка Compose
этого не подтверждает.

Официальные справочники: [Automatic HTTPS](https://caddyserver.com/docs/automatic-https),
[reverse_proxy и доверие к заголовкам](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy),
[TLS и внутренний CA](https://caddyserver.com/docs/caddyfile/directives/tls),
[ограничение тела запроса](https://caddyserver.com/docs/caddyfile/directives/request_body),
[секреты Compose](https://docs.docker.com/compose/how-tos/use-secrets/).

## Размещение данных сотрудников

Если учётные записи содержат ФИО или другие персональные данные сотрудников,
до рабочего запуска организация определяет оператора, правовое основание,
сроки хранения и круг доступа. Основную базу, загруженные документы, журналы и
резервные копии размещайте в инфраструктуре в России с учётом применимых
требований 152-ФЗ и правил локализации. Физическое местонахождение дисков,
резервных площадок и администраторского доступа подтверждает владелец сервера.
Сам файл Compose не подтверждает соблюдение этих требований.

Передачу документов внешнему API и трансграничную обработку нужно оценить отдельно
с ответственным за персональные данные. `OPENAI_ENABLED=0` является настройкой по
умолчанию; остальные функции приложения работают без OpenAI. Для разрешённого
подключения ключ записывают в `.secrets/openai_api_key`, включают
`OPENAI_ENABLED=1` и пересоздают `web` и `worker`. Не отправляйте персональные данные
в GPT до такого согласования; подробнее — [gpt.md](gpt.md).

Для изменения пустого файла ключа временно разрешите владельцу запись
(`chmod u+w .secrets/openai_api_key`), откройте его локальным редактором, затем
верните права `chmod 0444 .secrets/openai_api_key`. Не вставляйте ключ в аргументы
команды или историю оболочки. После настройки:

```sh
sh scripts/server.sh up -d --force-recreate web worker
```

## Что должен предоставить владелец перед рабочим переносом

Домен и DNS, доступ к серверу и firewall, разрешённый способ выдачи сертификата,
подтверждённое размещение данных и резервных площадок в России, доступ сервера к
образам GHCR, ответственных за учётные записи и резервирование. Доступы к внутренним
источникам и разрешение на внешний GPT нужны только для соответствующих интеграций.
Ни одно из этих значений не подставляется в репозиторий вместо владельца.
