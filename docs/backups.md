# Ежедневные резервные копии и восстановление

Для сервера используется отдельный контейнер из `Dockerfile.backup`: PostgreSQL 17.6 (`pg_dump` и `pg_restore`) и Restic 0.18.0. Веб-приложение, планировщик загрузок и резервирование работают независимо от браузера сотрудника.

## Что сохраняется

- Согласованный снимок PostgreSQL: показатели, версии наблюдений, ручные поправки, пользователи, настройки, задания и ссылки на публикации.
- Том `media`: исходные загруженные файлы, публикации и выпущенные отчёты.
- Манифест с датой UTC, версией формата и версией PostgreSQL.

Репозиторий Restic зашифрован. По умолчанию он расположен на сервере в `backups-prod/restic`, служебные отметки времени — в `backups-prod/status`. Пароль берётся из `.secrets/backup_password`; пароль БД — из другого секретного файла. Они не записываются в архив или GitHub. Сохраните пароль Restic в защищённом хранилище организации отдельно от сервера: без него восстановление невозможно.

`pg_dump` получает согласованный MVCC-снимок, затем Restic сохраняет файлы. Приложение записывает публикации и выпущенные отчёты как неизменяемые файлы до фиксации ссылки в БД. Поэтому такой порядок сохраняет файлы, на которые ссылается снимок. Не удаляйте и не меняйте файлы в томе `media` вручную во время копирования. Для внешней очистки или перемещения файлов сначала остановите процессы записи и дождитесь окончания резервирования.

Код и контейнеры восстанавливаются из GitHub/GHCR. Отдельно сохраните `.env.prod`, `.secrets`, настройки DNS/сертификатов организации и выбранные SHA образов. Секреты передавайте в собственное защищённое хранилище, а не в открытый репозиторий резервных копий.

## Расписание и проверка

После первого запуска контейнер делает первую копию сразу. Затем запускается ежедневно в `03:00` по `Europe/Moscow`; время задаёт `BACKUP_TIME` в `.env.prod`. Повтор после ошибки — через 15 минут. Изменение часов сервера не сдвигает календарное расписание. Docker должен работать постоянно.

```sh
sh scripts/server.sh ps
sh scripts/server.sh logs --tail 100 backup
sh scripts/server.sh exec backup /usr/local/bin/backup-healthcheck.sh
```

Проверка состояния контролирует работу планировщика и возраст последней успешной копии (не более 26 часов). Во время первого резервирования допускается такое же окно, но завершившаяся с ошибкой попытка сразу делает проверку неуспешной. После следующей успешной копии ошибка снимается. Код возврата `0` — проверка пройдена; ненулевой — проверьте журнал. Состояние Docker `unhealthy` само по себе не отправляет письмо: подключите оповещение к мониторингу организации.

Ручная копия без остановки приложения:

```sh
sh scripts/server.sh exec backup /usr/local/bin/backup-now.sh
```

Блокировка `flock` в каталоге резервных копий исключает параллельный запуск из планировщика и ручной команды. Повторная команда при занятой блокировке завершится с кодом `75`.

Список снимков и полная проверка чтения архива:

```sh
sh scripts/server.sh exec backup restic snapshots
sh scripts/server.sh exec backup restic check --read-data
```

Здесь `restic` — установленный двоичный файл; переменные репозитория и пароль доступны контейнеру через настройки и секретный файл. После каждой копии выполняется проверка структуры и чтение случайных 5% блоков. Затем сохраняются 30 дневных, 4 недельных и 12 месячных точек. Неудачная загрузка или проверка не удаляет предыдущие копии. При нехватке места исправьте причину, затем выполните ручную копию. Для крупных БД увеличьте размер `tmpfs /work` в Compose: туда помещается промежуточный `pg_dump`.

Локальная копия на том же сервере защищает от ошибок данных, но не от потери сервера. Организации нужен второй носитель или отдельное хранилище в России. Можно перенести весь зашифрованный каталог Restic на такой носитель, когда резервирование остановлено. Если настраиваете удалённый backend Restic, сначала создайте и проверьте его вручную, задайте соответствующие учётные данные и разрешите контейнеру доступ к нему. Производственная сеть `backend` изолирована; внешний доступ не открывается автоматически. Место хранения и порядок передачи согласуйте с ответственным за персональные данные.

## Безопасное извлечение снимка

Сначала выберите конкретный ID из `restic snapshots`. Команда восстановления принимает явный ID; `latest` не принимается, чтобы не перепутать снимки. Создайте отдельный пустой каталог на сервере:

```sh
mkdir -m 700 restore-staging
sh scripts/server.sh run --rm --no-deps \
  --cap-add CHOWN --cap-add FOWNER \
  -v "$PWD/restore-staging:/restore" backup restore SNAPSHOT_ID
```

Замените `SNAPSHOT_ID` выбранным ID. Права `CHOWN` и `FOWNER` нужны этому одноразовому контейнеру для восстановления владельцев и прав файлов; постоянному планировщику они не выдаются. Команда проверяет восстановленные файлы и пишет только в `/restore`; к рабочей БД она не подключается. Непустой каталог отклоняется. В результате:

```text
restore-staging/
  media/                         # исходные файлы и отчёты
  work/snapshot/database.dump    # PostgreSQL custom-format
  work/snapshot/manifest.txt     # сведения о копии
```

Если меняли `BACKUP_WORK` внутри образа, относительный путь снимка будет соответствовать этому каталогу. Каталог извлечения содержит незашифрованные персональные данные: ограничьте доступ и удалите его после проверки. Владелец файлов внутри может быть `root`; просматривайте их через `sudo`.

## Проверка восстановления без изменения рабочей базы

На сервере с работающим PostgreSQL можно загрузить дамп в отдельную тестовую БД. Имя `product_restore_check` используется только в примере. Убедитесь, что такой БД ещё нет:

```sh
sh scripts/server.sh exec db createdb -U product product_restore_check
sh scripts/server.sh cp restore-staging/work/snapshot/database.dump db:/tmp/product-restore.dump
sh scripts/server.sh exec db pg_restore -U product \
  --no-owner --no-acl --exit-on-error \
  --dbname=product_restore_check /tmp/product-restore.dump
sh scripts/server.sh exec db psql -U product -d product_restore_check \
  -c 'SELECT COUNT(*) FROM monitoring_observation;'
sh scripts/server.sh exec db rm /tmp/product-restore.dump
```

При другом `POSTGRES_USER` замените `product`. `createdb` отклонит уже существующее имя, а `pg_restore` остановится при ошибке. Сравните число записей и несколько контрольных значений с состоянием на дату снимка; откройте восстановленные документы. После проверки удалите только созданную тестовую БД:

```sh
sh scripts/server.sh exec db dropdb -U product product_restore_check
```

## Перенос проверенного снимка в рабочую систему

Это отдельная операция администратора в согласованное окно обслуживания. Не запускайте её, пока не проверили снимок в тестовой БД и не сделали дополнительную копию текущего состояния.

1. Запишите текущие SHA образов и сделайте ручную копию.
2. Остановите `web`, `worker`, `caddy` и планировщик `backup`; PostgreSQL оставьте работающим.
3. Восстановите дамп **в новую** БД с новым именем и проверьте её, как выше. Не используйте `pg_restore --clean` на рабочей БД.
4. Сохраните прежний том `media`. Создайте новый том и перенесите в него содержимое `restore-staging/media`, сохранив структуру каталогов. Дайте UID/GID `10001:10001` права на файлы приложения. Не выдавайте всем пользователям права `777`.
5. В копии Compose задайте новое имя БД и новый том `media`; используйте версию образа, совместимую со снимком. Не запускайте более старую версию кода на уже обновлённой схеме.
6. Запустите приложение, дождитесь миграций и `healthy`, проверьте вход, число записей, источники и отчёты. Затем включите `worker`, `backup` и доступ сотрудников.
7. Сохраните прежнюю БД и том до приёмки восстановления. При проблеме можно вернуть прежнюю конфигурацию, пока новая система не принимает изменения.

Проверяйте полный цикл восстановления регулярно и после существенного обновления схемы. Наличие файла архива без такой проверки не подтверждает возможность восстановления.
