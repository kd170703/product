# Защита входа и секретов

В серверном запуске включены HTTPS, ограничение попыток входа и обязательная двухфакторная аутентификация. В локальном запуске двухфакторная защита подключается по желанию сотрудника. После подключения она обязательна для этой учётной записи при любом режиме запуска.

## Вход и блокировки

`django-axes` хранит счётчики в PostgreSQL, поэтому перезапуск приложения не сбрасывает ограничение. По умолчанию 5 неудачных попыток блокируют вход на 30 минут для логина **или** IP-адреса. Это ограничивает как подбор одного пароля с разных адресов, так и перебор учётных записей с одного адреса. Неверный код второго фактора тоже учитывается. Ответ блокировки: HTTP 429 с `Retry-After` и объяснением на русском языке. Попытки во время блокировки не продлевают срок.

За общим адресом организации блокировка по IP может затронуть нескольких сотрудников. Администратор выбирает подходящие `DJANGO_AXES_FAILURE_LIMIT` и `DJANGO_AXES_COOLOFF_MINUTES`, оценивая реальную сеть. Успешный полный вход сбрасывает соответствующие счётчики.

На сервере с Caddy разрешено доверие к `X-Forwarded-For` только потому, что Caddy перезаписывает заголовок адресом реального клиента, а порт Django не опубликован. `TRUST_PROXY=1` нельзя использовать при прямом доступе к Django из недоверенной сети. В обычном локальном запуске заголовок игнорируется.

Проверив причину ограничения и личность сотрудника, администратор может снять блокировку логина и, если требуется, адреса:

```bash
scripts/server.sh exec web python manage.py axes_reset_username employee_login
scripts/server.sh exec web python manage.py axes_reset_ip 192.0.2.10
```

Не снимайте блокировку автоматически по просьбе неизвестного пользователя. Не включайте общий `axes_reset` в расписание: он удаляет действующие ограничения.

## Подключение второго фактора

1. Сотрудник входит с выданным паролем. На сервере с `DJANGO_REQUIRE_2FA=1` доступ к рабочим данным до завершения подключения закрыт.
2. На странице «Защита входа» подтверждает текущий пароль и запускает подключение.
3. Добавляет QR-код в локальное приложение-аутентификатор с поддержкой TOTP, например FreeOTP или Aegis. Альтернатива — ввод ключа вручную. QR-код создаётся на сервере без обращения к сторонним сервисам; SMS и номер телефона не используются.
4. Вводит действующий шестизначный код. Настройка действует 10 минут. Время телефона и сервера должно быть синхронизировано.
5. Сохраняет 10 резервных кодов в защищённом хранилище отдельно от телефона. Они показываются один раз, каждый действует для одного входа.

На странице входа выбирается код приложения или резервный код. Повторное использование уже принятого TOTP-кода запрещено; дождитесь следующего кода. Есть отдельная возрастающая задержка после неправильных попыток проверки TOTP и резервных кодов.

Для выпуска нового комплекта резервных кодов нужны текущий пароль и новый действующий код приложения либо неиспользованный резервный код. Все прежние резервные коды отменяются. Подключение 2FA немедленно делает недостаточными ранее открытые сеансы без второго фактора. Это распространяется на дашборд, API, файлы, отчёты и Django admin. Отдельного входа в admin по одному паролю нет.

При первом вводе в эксплуатацию администратор организует подключение сотрудников в доверенной сети. Включение обязательной 2FA не подтверждает личность владельца уже скомпрометированного пароля.

## Утрата телефона и восстановление

При наличии резервного кода сотрудник может войти самостоятельно. Смена подключённого телефона выполняется через администратора после проверки личности. Веб-страницы, позволяющей отключить второй фактор одним паролем, нет.

Администратор с доступом к серверу фиксирует обращение в журнале организации и выполняет:

```bash
scripts/server.sh exec web python manage.py reset_two_factor employee_login --reason "Личность проверена по внутренней процедуре, обращение 123"
```

Команда удаляет устройства и резервные коды только этой учётной записи и завершает её активные сеансы. В выводе указываются время, логин и обоснование; сохраните результат в журнале управления доступом. Не включайте в обоснование лишние персональные данные. Следующий вход в серверном режиме потребует повторного подключения. Для случая компрометации дополнительно смените пароль. Доступ к этой процедуре равнозначен административному доступу к серверу и должен быть ограничен.

## Секреты и хранение

`DJANGO_SECRET_KEY` обязателен: отсутствие, пустое значение и прежний известный запасной ключ останавливают запуск с `ImproperlyConfigured`. Автоматического запасного значения нет. Одновременно задавать переменную и файл с непустым значением нельзя.

Поддержаны `DJANGO_SECRET_KEY_FILE`, `POSTGRES_PASSWORD_FILE` и `OPENAI_API_KEY_FILE`. Серверная подготовка создаёт секреты в каталоге `.secrets`; они не включаются в Git или образ. Пустой файл ключа OpenAI допускается, поскольку интеграция необязательна. Пароль PostgreSQL и ключ Django сохраняйте в защищённом хранилище организации отдельно от сервера и резервной копии. Не меняйте их при обычном обновлении образа. Перед ротацией Django-ключа учитывайте завершение существующих сеансов и влияние на подписанные данные.

TOTP-ключи должны быть доступны серверу для проверки кодов, поэтому библиотека хранит их в базе в восстанавливаемом виде; резервные коды также являются секретами базы. Ограничьте доступ к PostgreSQL, файловой системе сервера и административным средствам. Шифрование дисков обеспечивает инфраструктура организации, шифрование резервных копий — Restic. Не публикуйте дампы, резервные коды, QR-коды или содержимое `.secrets`.

## Минимизация журналов

Обработчик Axes сохраняет агрегат попыток: логин, IP, время, число ошибок и путь. Тело формы, параметры GET, User-Agent и HTTP Accept не сохраняются. В журнальных сообщениях Axes логин и IP маскируются; отдельные бессрочные журналы успешных/неудачных входов Axes отключены.

При работающем worker раз в час удаляются агрегаты Axes и незавершённые настройки 2FA старше суток, а также истёкшие сеансы Django. Для ручного запуска:

```bash
scripts/server.sh exec web python manage.py cleanup_auth
```

Это технический срок хранения защиты входа; он не заменяет политику хранения данных организации. История наблюдений, ручных поправок и отчётов не удаляется этой процедурой. Логи Docker, Caddy, инфраструктуры и резервные копии имеют отдельные сроки хранения — см. [размещение данных](data-localization.md).

## Внешний API GPT

`OPENAI_ENABLED=0` используется по умолчанию, в том числе на сервере. Наличие ключа не разрешает отправку данных. Для включения нужны явное `OPENAI_ENABLED=1`, серверный ключ, модель и решение оператора о допустимых данных и условиях передачи. При отключении проверка выполняется и на странице, и в серверной функции извлечения; остальные возможности приложения работают. См. [настройку GPT](gpt.md) и [размещение персональных данных](data-localization.md).

## Проверки

Автоматические тесты используют настоящие модели Axes/OTP и алгоритм TOTP: блокировка после ошибок, новый клиент с тем же счётчиком, проверка и повторное использование кода, одноразовые резервные коды, подключение/истечение настройки, CSRF, запрет обхода через admin/API и сеансы без OTP, отзыв сеансов при серверном восстановлении, отсутствие секретов в журналах Axes и остановка без ключа Django. Это не аудит безопасности инфраструктуры и не проверка реального устройства сотрудника.
