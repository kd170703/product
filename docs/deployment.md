# Развёртывание и эксплуатация

## Контейнеры и постоянные данные

`compose.yaml` запускает три сервиса: PostgreSQL, Django/Gunicorn и отдельный worker расписания. Web начинает слушать порт после миграций, идемпотентного `bootstrap` и `collectstatic`. Worker зависит от успешной проверки `/health/` web и не запускает миграции. Контейнеры имеют политику `restart: unless-stopped`; после перезапуска Docker Desktop они возобновят работу, если ранее не были явно остановлены. Для непрерывного расписания Docker/сервер должны оставаться запущенными.

Том `pgdata` содержит PostgreSQL, `media` — исходные публикации, импорты и выпущенные отчёты. Оба подключаются независимо от жизненного цикла контейнера. Папка `incoming` смонтирована с хоста только для чтения. Не удаляйте тома при остановке и не рассчитывайте на внутреннюю файловую систему web как на хранилище данных.

Фоновые задания используют очередь PostgreSQL, ограничение одного активного задания на источник, lease и advisory lock. После аварийного завершения процесса зависшее задание возвращается на повтор после истечения lease; число попыток ограничено. Ошибка источника не удаляет последние корректные наблюдения.

## Настройки окружения

| Переменная | Назначение |
| --- | --- |
| `DJANGO_SECRET_KEY` | Случайный секрет Django; обязателен, хранится только на сервере |
| `POSTGRES_PASSWORD` | Пароль БД; обязателен, не совпадает с секретом Django |
| `POSTGRES_DB`, `POSTGRES_USER` | Имя базы и роль; по умолчанию `product` |
| `POSTGRES_HOST`, `POSTGRES_PORT` | Compose задаёт `db:5432` |
| `DJANGO_ALLOWED_HOSTS` | Разрешённые имена приложения, без схемы/порта |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | Полные доверенные origins с `https://` |
| `DJANGO_HTTPS` | `1` за работающим HTTPS reverse proxy; локально `0` |
| `TRUST_PROXY` | `1`, только если доверенный reverse proxy задаёт `X-Forwarded-Proto` |
| `OPENAI_API_KEY`, `OPENAI_MODEL` | Необязательная серверная настройка GPT |
| `IMPORT_WATCH_DIR` | В Compose `/app/incoming` |

Смена `POSTGRES_PASSWORD` в `.env` не меняет пароль существующей роли в уже созданном PostgreSQL. Согласованно измените роль и окружение, затем пересоздайте web и worker. Смена имён базы/роли требует миграции данных, а не только редактирования `.env`.

## Доступ коллег и HTTPS

Локальный Compose публикует только `127.0.0.1:8000`. Для внутреннего сервера поместите приложение за существующий HTTPS reverse proxy организации с подходящим DNS-именем и сертификатом. Добавьте это имя в `DJANGO_ALLOWED_HOSTS`, `https://имя` в `DJANGO_CSRF_TRUSTED_ORIGINS`, задайте `DJANGO_HTTPS=1`. При доверенном proxy, который очищает пользовательский и выставляет собственный `X-Forwarded-Proto`, используйте `TRUST_PROXY=1`.

Не публикуйте PostgreSQL наружу. Прямой доступ к `media` через nginx/другой сервер не настраивайте: скачивание рабочих файлов и отчётов должно проходить через аутентифицированные маршруты приложения. Оставьте `DJANGO_DEBUG=0`. Настройте доступ к серверу и резервным копиям по правилам организации. Для production рекомендуется отдельная ограниченная роль runtime БД и отдельный процесс применения миграций; в демонстрационном Compose используется роль-владелец PostgreSQL для простоты первого запуска.

## Резервное копирование

Резервируется согласованный комплект PostgreSQL и `media`. На время создания копии остановите **оба** пишущих процесса web и worker; PostgreSQL оставьте включённым. Пошаговые команды PowerShell приведены в README. Формат `pg_dump -Fc` переносим между совместимыми инсталляциями PostgreSQL; предпочтительно восстанавливать на той же основной версии или более новой поддерживаемой версии после отдельной проверки.

`docker compose cp` переносит бинарный дамп без текстового перекодирования PowerShell. Архив `media.tar.gz` создаётся контейнерным `tar`, не через перенаправление stdout в Windows. Перед восстановлением остановите процессы, проверьте комплект и сохраните текущую резервную копию. Восстановление заменяет базу через `pg_restore --clean --if-exists` и содержимое `media` через архив. Файлы `incoming` и `.env` сохраняются отдельно, если это требуется для восстановления процесса.

Периодически проверяйте восстановление на отдельном экземпляре: вход, количество наблюдений, версионность, один исходный файл и один выпущенный DOCX/XLSX. Наличие дампа без проверки восстановления не является подтверждённым восстановлением.

## Обновления и диагностика

Перед обновлением сохраните резервную копию и изучите новые миграции. `docker compose up -d --build` пересобирает образ, web применяет миграции. Для крупных схемных изменений остановите worker, выполните обновление web, проверьте работоспособность и запустите worker. Не обновляйте основную версию PostgreSQL простой заменой тега: требуется отдельная миграция PostgreSQL.

Диагностика: `docker compose ps`, `docker compose logs --tail 100 web worker db`, `docker compose exec web python manage.py check`. Полные логи могут содержать сведения об источниках; не публикуйте их без проверки. Ключ OpenAI и пароли нельзя включать в URL источников, код, снимки экрана или отчёты.

Официальные сайты могут ограничивать загрузки по сети, региону, User-Agent или временной политике. Не выключайте проверку TLS и не подменяйте данные. Сохраните точную ошибку, зарегистрируйте официальный файл и проверьте его через тот же адаптер локального импорта. HTTP-сбой и методическая приостановка определения — разные состояния.

## Прокси и дополнительный CA

Обычный Windows/Docker Desktop использует стандартные корневые сертификаты. При корпоративном TLS proxy нужен утверждённый организацией CA. Dockerfile поддерживает необязательный BuildKit secret `proxy_ca` только на шаге установки Python-зависимостей. Не встраивайте секреты или session-specific CA в слои образа. Пример отдельного локального override-файла:

```yaml
services:
  web:
    build:
      secrets:
        - proxy_ca
    environment:
      HTTPS_PROXY: ${HTTPS_PROXY}
      HTTP_PROXY: ${HTTP_PROXY}
      NO_PROXY: localhost,127.0.0.1,db,web
      SSL_CERT_FILE: /run/proxy-ca.pem
      REQUESTS_CA_BUNDLE: /run/proxy-ca.pem
    volumes:
      - ${PRODUCT_CA_BUNDLE}:/run/proxy-ca.pem:ro
  worker:
    build:
      secrets:
        - proxy_ca
    environment:
      HTTPS_PROXY: ${HTTPS_PROXY}
      HTTP_PROXY: ${HTTP_PROXY}
      NO_PROXY: localhost,127.0.0.1,db,web
      SSL_CERT_FILE: /run/proxy-ca.pem
      REQUESTS_CA_BUNDLE: /run/proxy-ca.pem
    volumes:
      - ${PRODUCT_CA_BUNDLE}:/run/proxy-ca.pem:ro
secrets:
  proxy_ca:
    file: ${PRODUCT_CA_BUNDLE}
```

`PRODUCT_CA_BUNDLE` указывает на полный доверенный CA bundle с корневыми сертификатами и корпоративным CA. Запуск: `docker compose -f compose.yaml -f compose.proxy.yaml up -d --build`. Не сохраняйте адреса с паролями/ключами в отслеживаемых файлах. Proxy-настройка сетевого доступа не гарантирует доступ к сайтам Банка России, Росстата или ФНС: результат проверяется отдельным реальным запросом.

## Требования, зависящие от владельца

- Разрешённый production-сервер, DNS, HTTPS, эксплуатационный доступ и политика резервных копий.
- Согласование определений спорных статистических показателей, временных периодов и территорий; утверждённая версия методики ИРФК.
- Согласованная папка/формат будущих внутренних выгрузок и права процесса на чтение; данные онлайн-зачёта.
- Рабочий OpenAI API key, разрешение на передачу выбранных документов и доступ к нужной модели, если панель GPT используется.
- Доступ к официальным публикациям из серверной сети либо сохранённые официальные файлы с указанием источника и даты.
